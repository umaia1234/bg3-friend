# BG3 Friend 플레이 준비 절차

이 문서는 Windows에서 BG3를 플레이하며 Codex에게 시작·연결 준비를 맡기는 사용자를 위한 실행 지침입니다. 같은 스킬 폴더의 `project.local.json`에 `nativeExe`가 있으면 Windows 앱을 사용하고, 없으면 등록된 WSL 소스를 사용합니다. 상세 설치 방법은 공개 저장소의 `docs/SETUP.ko.md`를 읽습니다. 앱 ZIP과 스킬 등록용 공개 소스는 별개입니다.

## 미설정 항목 처리

먼저 현재 상태를 읽습니다. 이미 설치·승인·선택된 항목은 재설치하거나 같은 질문을 반복하지 않습니다. 점검 결과와 현재 대화를 대조하여 실제 누락 항목만 한 번에 정리합니다.

| 확인할 것 | 없거나 선택이 필요한 경우 |
|---|---|
| Windows Computer Use | 해당 작업에서 네이티브 창을 제어할 도구가 실제로 있는지 확인합니다. 없으면 연결·사용 가능한 Windows 작업으로 전환이 필요하다고 설명하고 먼저 물어봅니다. |
| BG3·Steam·프로젝트 경로 | 이미 설치된 게임과 이 저장소를 찾습니다. 다른 드라이브는 Steam `libraryfolders.vdf`와 `appmanifest_1086940.acf`로 확인합니다. 복수 설치나 다른 계정은 사용자 선택을 받습니다. 게임 구매·대용량 다운로드를 자동 시작하지 않습니다. |
| Windows 앱 | 등록된 `nativeExe`와 배포 폴더 전체를 확인합니다. 실행 파일이나 내장 패키지가 없으면 받은 ZIP·확인된 설치 폴더를 찾고 복사·교체 범위를 먼저 설명합니다. 앱에는 Python/Tk가 포함되어 있으므로 별도 Python·WSL을 설치하지 않습니다. 새 앱으로 바꾸기 위해 기존 파티 대화를 임의로 종료하지 않습니다. |
| Native 설정·Codex CLI | 앱의 게임·프로필·Codex 경로와 전송 동의를 확인합니다. native 앱은 선택된 Windows Codex CLI를 사용합니다. WSL 로그인만으로 이 로그인까지 확인했다고 말하지 않습니다. 없는 Codex 설치와 직접 로그인 단계는 먼저 설명합니다. |
| WSL 소스 실행 | 이 경로를 쓰도록 등록된 경우에만 배포판·WSL Python·Codex CLI를 점검합니다. 설치 대상·재시작이 필요하면 먼저 설명합니다. 스킬은 `--io`로 승인된 프로필을 지정하며 Windows 사용자 전체에서 하나의 프로필만 있다고 가정하지 않습니다. |
| 소스 실행의 Windows Python·Tk | `windowsPython`이 있으면 그 경로를 `--gui-python`으로 사용합니다. 없으면 소스 실행기의 Python 검색 결과를 확인합니다. Python 3.11 이상과 Tk가 필요하며 특정 `Python311` 위치에 고정하지 않습니다. 실제 누락된 구성만 승인 후 준비합니다. |
| Script Extender·BG3Friend.pak·모드 등록 | 실제 설치 파일과 `Public/modsettings.lsx`의 BG3 Friend UUID를 확인합니다. 설치·재설치가 필요하면 영향받을 게임 파일, 백업 위치, 게임 종료 필요를 설명하고 승인받습니다. |
| LSLib·.NET·빌드 도구 | **소스에서 모드를 제작할 때만** 설치 안내의 도구를 확인합니다. Windows 앱의 내장 PAK 설치나 이미 설치된 모드 실행을 위해 빌드 도구부터 설치하지 않습니다. |
| Codex 로그인 | native는 앱의 **상태 확인**, 소스는 해당 배포판의 `doctor.py --scope account` 또는 `codex login status`로 확인합니다. 필요하면 사용자에게 알려 본인의 브라우저 인증을 직접 마치게 합니다. 인증 창·암호·OTP를 대신 입력하거나 인증 파일을 읽지 않습니다. 로그인 확인은 모델 응답 검증이 아닙니다. |
| 세이브·동료·전투 제어 | 현재 요청과 게임에 표시된 선택을 사용합니다. 정해지지 않은 선택만 물어봅니다. 앞으로의 기본값 저장은 사용자 요청이 있을 때 로컬 `preferences`에 기록합니다. |

질문은 실행할 변경이 보이게 구체적으로 합니다. 예: “Windows Python과 BG3 Friend 모드 등록이 빠져 있습니다. Python 설치 후 게임을 종료하고, 기존 파일을 백업한 뒤 모드를 등록해도 될까요?” 경로·세이브·동료는 실제 확인한 후보 이름을 제시합니다. 설치하지 않기로 한 항목을 임의로 대체하거나 계속 재시도하지 않습니다.

승인을 받으면 해당 항목을 완료하고 다시 점검합니다. 설치기·Steam·게임의 화면 조작은 Computer Use로 수행합니다. Python·WSL·패키징·파일 복사·진단 명령은 명령 실행 도구를 사용합니다. 실행 도구가 필요한 명령을 Windows Run이나 터미널 UI에 입력하는 우회 절차를 만들지 않습니다. UAC·인증·재시작처럼 사용자가 직접 해야 하는 단계가 나오면 정확히 그 단계만 넘기고, 완료된 뒤 기존 절차를 이어갑니다.

`modsettings.lsx`가 없는 최초 설치는 먼저 사용자 승인 범위에서 BG3를 주 메뉴까지 열어 프로필을 만든 뒤 정상 종료하고 설치합니다. 세이브 백업과 모드 설치는 게임이 닫힌 상태에서 합니다. 플레이 중인 게임에 저장하지 않은 진행이 있으면 종료 전에 사용자에게 확인합니다. 백업·설치·로그인 점검을 통과한 뒤 게임 시작으로 돌아옵니다.

## Windows 앱에서 승인된 설정 마치기

1. 기존 **BG3 Friend** 메인 창을 찾습니다. 없으면 등록된 앱을 엽니다. `Start`가 설정 미완료로 exit 1을 반환해도 열린 설정 창에서 계속할 수 있습니다. `--overlay` 창과 메인 설정 창을 구분합니다.
2. **자동 찾기**의 결과와 **게임 폴더**, **게임 프로필**, **Codex 실행 파일**, **모델**을 읽습니다. 등록된 개인 경로나 실제 파일 선택 창의 후보를 사용합니다. 발견한 값만으로 새 모델·계정·게임 설치를 선택하지 않습니다.
3. 사용자에게 승인받은 경로를 **찾기** 또는 입력란에 적용합니다. 전송 동의는 안내의 데이터와 사용량을 설명하고 승인받았을 때만 체크합니다. **설정 저장** 후 **상태 확인**을 누릅니다. `nativeConfigRoot/settings.json`을 직접 써서 동의나 선택을 우회하지 않습니다.
4. 모드 설치가 필요하면 기존 게임·대화가 종료됐는지 확인하고 **모드 설치·업데이트**를 엽니다. **모드 변경 확인**의 실제 파일·백업 경로를 읽어 이미 승인된 변경과 대조합니다. 범위가 같으면 **적용하기**를 누르고 완료 뒤 재점검합니다. 다른 변경이 추가되면 그 변경만 먼저 묻습니다. 기존 Script Extender를 재설치할 필요가 없으면 DLL을 새로 고르지 않습니다.
5. Codex 로그인은 앱에 지정된 실행 파일의 계정으로 진행하며 본인 인증은 사용자에게 넘깁니다. 필요한 단계가 끝나면 **상태 확인**을 다시 수행합니다. 소스 경로의 계정·인증 파일을 native 앱 폴더로 복사하지 않습니다.
6. 설정이 준비되고 파티 대화가 꺼져 있으면 **파티 대화 시작**을 누릅니다. 이미 helper가 살아 있으면 그 연결을 유지합니다. 이어서 게임·세이브·오버레이·동료 선택을 아래 절차로 확인합니다. 메인 창만 열린 상태는 시작 완료가 아닙니다.

앱은 기본적으로 Windows에 등록된 **Saved Games 폴더/BG3Friend/settings.json**을 사용합니다. 보통 `%USERPROFILE%/Saved Games/BG3Friend`이며 경로를 환경변수만으로 추측하지 않습니다. 사용자 지정 `nativeConfigRoot`가 있으면 그 폴더를 사용하고 설치·복구 기록은 그 아래 `install`에 둡니다. 이전 설정 위치에 관리 중인 설치가 있으면 새 위치에서 별도 설치 기록을 만들지 말고 같은 명시 `nativeConfigRoot`를 유지하거나 전환 절차를 먼저 확인합니다. 설정 파일 버전이 맞지 않거나 손상됐으면 기존 내용을 삭제하지 말고 앱이 제시하는 보존·재설정 절차와 변경을 먼저 설명합니다.

## 화면에서 플레이 준비

### 1. 현재 화면과 프로세스 선택

사용 가능한 Computer Use 스킬을 읽어 초기화하고 반환된 앱·창에서 BG3 또는 LariLauncher를 고릅니다. 창을 전면에 둔 뒤 화면이나 접근성 트리를 읽습니다. 매번 관찰 → 한 동작 → 재관찰 순서를 따릅니다. 이전 실행의 좌표나 다른 창의 요소 번호를 재사용하지 않습니다.

이미 게임 세션과 친구가 연결되어 있으면 그 세션을 유지합니다. 명령 확인을 위해 게임을 껐다 켜거나 세이브를 다시 불러오지 않습니다. 시작 스크립트가 기존 프로세스를 재사용했더라도 실제 오버레이·현재 상태 확인은 수행합니다.

### 2. 런처와 주 메뉴

LariLauncher에서는 현재 DX11/Vulkan 선택을 유지하고 실제 **플레이** 버튼을 누릅니다. 표시된 안내는 내용을 먼저 읽습니다. 읽은 단순 안내 닫기와 설치·계정·파일 변경 동의는 구분하며, 알 수 없는 데이터 문제를 임의의 파일 삭제·검사 복구로 해결하지 않습니다. “다시 보지 않음” 같은 설정을 시작 편의상 바꾸지 않습니다.

**데이터 불일치**가 나오면 **파일 목록 열기** 또는 런처 Cache의 현재 버전 `steam_<버전>_alteredFiles.txt`를 읽고 승인된 설치와 대조합니다. 상세 경로는 `docs/SETUP.ko.md`의 해당 절차를 사용합니다. `DWrite.dll`, Script Extender 설정, `BG3Friend.pak`처럼 확인된 추가 모드 파일만 있고 설치 진단이 통과했다면 내용을 설명하고 안내를 닫아 계속합니다. 경고 자체를 게임 손상으로 단정하거나, 모르는 파일 변경까지 정상이라고 판단하지 않습니다.

게임 창을 다시 선택하여 로딩을 기다립니다. **진행하려면 아무 키나 누르십시오** 화면에서는 키를 보내고 화면이 바뀌었는지 확인합니다. 입력이 반영되지 않았으면 창 활성화·포커스를 다시 확인한 뒤 한 번 재시도합니다. 키 전송 성공만으로 주 메뉴에 도착했다고 말하지 않습니다.

### 3. 세이브 불러오기와 모드

- 사용자가 특정 세이브를 지정했다면 **게임 불러오기**에서 화면에 표시된 이름·캠페인으로 찾아 선택합니다.
- 사용자가 **이어하기**를 요청했다면 그 선택을 사용합니다. 이름 없는 “하자” 요청에서 여러 세이브 중 최신 파일을 임의로 고르지 않습니다.
- 선택이 없으면 보이는 세이브 후보를 확인하고 먼저 물어봅니다. 답을 받으면 Codex가 UI로 불러오기를 마칩니다. 사용자에게 전체 조작을 떠넘기지 않습니다.
- 모드 확인 창이 나오면 해당 세이브의 BG3 Friend 사용 여부를 읽습니다. 사용자에게 승인된 설정에 맞게 활성화하고 진행합니다. 모드가 누락되어 있으면 설치 절차로 돌아가 먼저 확인받습니다. 다른 모드를 임의로 비활성화하지 않습니다.
- 새 게임·저장·삭제·덮어쓰기는 시작 절차에 포함되지 않습니다. 별도의 사용자 요청이 있어야 합니다.

로드가 끝나면 `-Action Status`와 실제 게임 화면을 함께 확인합니다. 오래된 세션 파일은 성공 증거가 아닙니다. 신선한 snapshot이 없으면 게임이 아직 로딩 중인지, 모드가 활성화됐는지, Script Extender가 로드됐는지 확인합니다. 상태가 변하지 않으면 원인을 진단하며 같은 버튼을 반복하지 않습니다.

### 4. 친구 채팅과 동료 연결

게임 창이 전면에 있을 때 미니맵 아래 반투명 채팅을 찾습니다. 채팅은 native 앱의 `BG3Friend.exe --overlay` 또는 소스 방식의 `pythonw.exe`가 표시하는 별도 창입니다. 새 창 목록에서 **BG3 Friend · 파티 대화** 제목의 창을 식별하고 그 창을 대상으로 조작합니다. **BG3 Friend** 제목의 메인 설정 창과 구분하고, 오버레이 좌표를 게임 창 좌표로 보내지 않습니다. 다른 앱이 전면이면 채팅이 숨으므로 게임을 활성화한 후 창 목록을 갱신합니다. 화면 밖으로 가려졌거나 게임이 최소화된 상태를 연결 실패와 구분합니다.

맡길 동료가 정해졌으면 **··· → 해당 동료** 또는 **함께하기**를 사용합니다. 설정되지 않았다면 실제 파티원 중 누구를 맡길지 먼저 물어봅니다. 사람 아바타나 다른 플레이어를 동료로 선택하지 않습니다. 초상화를 클릭하는 것과 친구 채팅의 동료 선택은 별개입니다.

탐험 제어 중에는 해당 동료의 파티 초상화 연결이 해제됩니다. 일시 정지·종료 시 원래 파티 연결로 돌아갑니다. 사용자가 게임에서 직접 파티를 다시 묶은 `party_group_changed` 상태는 수동 조작 의사로 취급합니다. 재개 요청이 있을 때만 채팅 메뉴에서 해당 동료를 다시 선택합니다.

첫 만남 카드는 실제 대화가 끝난 뒤 나타나며, 파티 합류 전에는 선택만 기억합니다. **합류 기다리는 중**은 정상적인 대기 상태입니다. 파티에 아직 없는 캐릭터를 연결 완료로 보고하거나 영입 대화를 임의로 진행하지 않습니다. 이미 **직접 할게**로 선택한 동료를 시작 확인 때문에 다시 연결하지 않습니다.

전투 제어 선택이 정해져 있으면 **전투도 맡기기** 체크 상태를 먼저 보고 일치할 때 그대로 둡니다. 첫 연결에서 선택이 없다면 한 번 물어봅니다. 전투는 게임 AI, 대화·탐험 판단은 Codex가 맡고 채팅과 파티·주변 정보가 Codex에 전달되어 사용량이 발생함을 설명합니다.

새로 불러온 세션에서 이번에 승인된 동료 연결은 UI로 시작합니다. 사용자가 명시적으로 쉬게 한 기존 세션은 재개 요청 없이 해제하지 않습니다. 로컬 `preferences`는 원하는 세이브·동료·전투 선택을 기록하는 자료이며 게임 자체의 저장된 선택을 덮어쓰는 명령이 아닙니다.

### 5. 입력 가능 여부와 완료 확인

사용자가 보낼 실제 문장을 지정했으면 채팅 입력란을 클릭하고 포커스를 확인한 뒤 그 문장만 입력·전송합니다. 단지 연결을 시험하려고 “안녕” 같은 문장을 만들어 보내지 않습니다. 사용자가 응답 시험을 원하면 시험 방법을 합의한 뒤 현재 세션의 실제 응답·오류를 확인합니다. 창을 띄우거나 호출 횟수가 늘어난 것만으로 응답 성공을 주장하지 않습니다.

일반적인 시작 완료는 **게임 세션 갱신 + 오버레이 표시 + 사용자 의도와 일치하는 동료 연결/대기 상태**입니다. 마지막에 현재 세이브·동료·준비 상태와 남은 사용자 조작이 있을 때 그 한 가지를 짧게 안내합니다. 실제 모델 답변을 확인하지 않았다면 그 검증을 했다고 말하지 않습니다.

빠진 선택을 묻거나 인증을 기다리는 동안은 완료가 아닙니다. 답이 오면 중단한 단계부터 이어갑니다. 영입 전 대기처럼 사용자가 선택한 정상 상태는 그대로 유지합니다. 준비 후의 기다림은 기존 runner가 맡으므로 Codex 예약 자동화나 반복 모델 호출을 만들지 않습니다.

## 종료·복구

잠시 멈춤은 **··· → 잠깐 쉬기**, 전체 친구 종료는 **··· → 대화 종료** 또는 native 메인 창의 **대화 중지**입니다. 게임까지 닫아 달라는 요청이 없다면 게임은 유지합니다. 종료 후 runner·오버레이 상태를 확인합니다. 강제 프로세스 종료나 `runner.lock`·`runner-claim` 삭제는 정상 종료의 대체가 아닙니다.

부분 실행·오류는 현재 프로세스, 최근 heartbeat, 현재 세션의 오류를 함께 확인합니다. 로그에서 필요한 오류 구간만 읽고 인증 자료나 전체 대화를 출력하지 않습니다. 원인을 확인한 다음 사용자 요청 범위 안에서 복구하고, 새 설치·설정 변경이 필요해지면 변경 내용을 먼저 물어봅니다.

`game_connection`은 게임 연결, `model_connection`과 `error_code`는 모델 연결을 설명합니다. 게임 snapshot이 신선한 채 로그인·사용량·모델 오류가 난 경우 세이브를 재로드하지 않습니다. `retrying`은 runner의 제한된 재시도 상태이므로 별도 반복 실행이나 가짜 채팅을 만들지 않습니다. 로그인·모델 설정을 고쳤고 사용자에게 재연결을 요청받았다면 native 메인 창에서 **대화 중지** → 종료 확인 → **설정 저장** → **상태 확인** → **파티 대화 시작** 순서로 이어갑니다. 실행 중인 runner가 설정 저장만으로 새 모델·경로를 읽는다고 가정하지 않습니다.

게임 연결이 끊겼으면 실제 게임·모드·snapshot 갱신을 확인하고, 모델 오류라면 로그인·모델·사용량 안내를 확인합니다. 응답 성공은 이번 세션에서 성공한 실제 결과로만 판단합니다. 단순 진단·로그인·배포 smoke 검사는 모델 응답 증거가 아닙니다.
